## B. Playback architecture and phase transitions

`ScreenRoom` owns a persistent `ProjectorMusic` component and one hidden native audio element. Its controller is independent of SceneStage and is identified by room+phase for lobby/finished and room+roundID for questions. It does not depend on scene ID, submission count, or the identity of each incoming `view` object. Re-pairing disposes the old room's controller. Default OFF is not persisted across reloads.

| Phase | Enabled behavior |
| --- | --- |
| `lobby` | Fetch lobby.mp3, start at zero, loop. |
| `active` | Stop lobby immediately; wait for the first promoted visual, then fetch the single question.mp3 definition and align to server elapsed round time. |
| `revealed` | Silence, including the sixth individual result. |
| `ready` | Silence; no lobby resumption or music prefetch between questions. |
| `finished` | Fetch lobby.mp3 anew, start at zero, loop. |

SceneStage only notifies the projector when ready content is promoted; it does not own or await audio. A delayed opening video therefore keeps question music silent until the visual experience begins. If video fails or a native scene supersedes it, the visible fallback/native content counts as that experience. Media fetch/decode delay is then compensated by seeking to `(estimatedServerNow - startedAt) / 1000`; it never shifts the soundtrack origin or extends a deadline.

The controller takes round ID, startedAt/deadlineAt, phase and the existing useRoom clock offset. An independent deadline timeout plus100ms watchdog stops and unloads the track even if the closing state update is missed. Offset correction re-arms the timeout; playback drift above350ms is corrected. An aligned seek completes before play. New rounds get a fresh source position; scene transitions preserve the current source/element. Looping is restricted to lobby/finished. A short question file ends in silence and reports that it ended; it is not looped/restarted to fill40 seconds.

OFF pauses immediately, aborts fetch, clears the source and revokes its Blob URL. Async callbacks carry a generation guard; late responses/play promises cannot revive a former phase or disabled track. Decode/network/policy errors are handled without changing gameplay. On disconnect the track stops; reconnect requires a fresh authoritative view, then seeks to the current round position. Refresh retains pairing but music returns to OFF until another explicit click.

The projector now has one **Bật nhạc / Tắt nhạc** toggle and a separate status message. The old video-audio control is replaced; scene videos remain muted. Loading, actual `playing`, silent waiting, blocked playback, unavailable media and early end are distinguished. The status remains with the controls, including fullscreen; no volume slider was added.

## E. Security and autoplay

`GET /api/screen/rooms/:code/music/:track` uses the existing bearer-session validation. Only an unexpired, unrevoked screen session bound to that room is accepted. Admin/team/other-room tokens are forbidden. The only track selectors are `lobby` and `question`; filesystem lookup uses a fixed filename map and realpath containment, including escaping-symlink rejection. There is no public static music directory.

Lobby delivery is allowed only in lobby/finished. Question delivery additionally requires `?roundId=<current-id>`, active phase, open current round and `started_at <= now < deadline_at`; this guard rejects new requests even if the close callback is delayed. Every request rechecks authorization before sending bytes; forbidden phase requests do not probe file availability. Responses are audio/mpeg, private/no-store, nosniff and same-origin. Client fetch uses Authorization header, no query token, no stored/shared cache, no credentials or unreleased prefetch. Authorization controls new delivery; bytes already legitimately delivered cannot be recalled.

Audible playback is requested only after operator intent is ON. The UI reports actual playback from `playing`, not merely from the toggle. Chrome's normal click activation path was exercised without its autoplay-bypass flag; deterministic `NotAllowedError` injection separately verifies the blocked state and recovery after permission is granted. Async audible playback may still be denied by browser/site policy. OFF/ON retries and the status explains denial; this does not stop visuals, deadlines or scoring. Refresh deliberately requires a new click. Browser guidance: [Chrome autoplay](https://developer.chrome.com/blog/autoplay/), [WebKit user gesture policy](https://webkit.org/blog/6784/new-video-policies-for-ios/).

JavaScript timers are not a physical real-time guarantee if the OS/browser suspends execution. The independent deadline proof covers missed state delivery while JavaScript continues running. Actual Mac background/suspend, browser permissions and speaker output remain manual acceptance items; no acoustic measurement or Safari/iOS autoplay pass is claimed.
