## 3. Mode A — Mac + Cloudflare Quick Tunnel (authorized testing only)

**Content rule:** never tunnel `npm start` (production montages: rights unresolved, RELEASE-READINESS
§4). Use `npm run trial`: the six production timelines' **timing** (release offsets, scene kinds,
transitions, video durations) with generated test-pattern clips of about the same sizes (28 clips,
11.0 MB vs 10.8 MB) and neutral text. `server/trial-synthetic.test.ts` asserts that no production
answer, text, credit, source or asset id is in it, and `npm run e2e:trial` (`e2e/trial-isolation.mjs`,
17 checks, including a self-test that the scanner flags real production content) runs the real trial server: STATIC_DIR pointed at `server/media`, `server/content` or
`media/` is refused; "mode" variables (`HC_MODE`, `NODE_ENV`, `QUESTIONS`, `MEDIA_ROOT`) are ignored; a
database written by the production server is recovered with synthetic scenes only; all six synthetic
questions are played as real 60 s rounds and none of 243 state frames or 28 served clips contains a
production answer, scene text, credit, URL, creator, asset id, file name or clip (sha256 against all 29
MP4s); every production asset id (196 requests) gets 403 and 72 production/attribution paths return
only the SPA index or 404.

```bash
# once
brew install cloudflared                      # or the release binary from github.com/cloudflare/cloudflared
cd ~/mln131_game && npm ci && npm run build  # production build; never the Vite dev server

# terminal 1 — synthetic server on loopback only (no router port forwarding, no LAN exposure)
export ADMIN_PASSWORD="$(openssl rand -base64 18)"; echo "admin password: $ADMIN_PASSWORD"
HOST=127.0.0.1 PORT=3001 TRUST_PROXY=loopback npm run trial
caffeinate -dimsu &                           # keep the Mac awake during the trial

# terminal 2 — temporary public HTTPS URL (prints https://<random>.trycloudflare.com)
cloudflared tunnel --no-autoupdate --url http://127.0.0.1:3001
#   if UDP is blocked on the network: add --protocol http2
```

Verify (from a different network, e.g. a phone hotspot):

```bash

BENCH_TARGET=$URL BENCH_ADMIN_PASSWORD="$ADMIN_PASSWORD" BENCH_LABEL=session/quick-tunnel npm run bench
#   reports socket transports (must be "websocket … over wss") and the media headers
#   (cache-control must stay "private, no-store"; cf-cache-status must not be HIT)
```

Manual checks with phones (MANUAL): open `$URL/admin` on the laptop and `$URL/?room=CODE` on phones on
4G/5G; play one synthetic round; with phone A enter 11 wrong admin passwords → "too many attempts",
then phone B must still get "wrong password" (proves per-client rate limits through Cloudflare).

Limits (Cloudflare documentation, checked 2026-10-21):
- Quick Tunnels are for testing and development: **no uptime guarantee**; the hostname is random and
  changes on every start; the URL dies when `cloudflared` stops; at most 200 concurrent requests
  (enough for ~8 devices). Source: developers.cloudflare.com/cloudflare-one/…/trycloudflare/.
- Video: Cloudflare's Free-plan terms restrict serving video/large files through its proxy, Tunnel
  public hostnames included (developers.cloudflare.com/fundamentals/reference/policies-compliances/
  delivering-videos-with-cloudflare/). Keep tunnel tests short and synthetic; Mode A is **not** a
  classroom hosting option.
- Cloudflare appends the visitor IP to `X-Forwarded-For`; `TRUST_PROXY=loopback` then rate-limits the
  real visitor (EXPECTED from the documented behaviour and the append-proxy unit test; **not verified on
  a real tunnel** — the manual two-phone check above verifies it).
- The Mac must stay on, awake and on the network; the session survives a server restart (same
  `DB_PATH`), not a tunnel restart (new URL).
- No CSP/HSTS headers in Mode A (Caddy adds them in Mode B). Stop the tunnel after testing.

Obstacles to plan for: "**Out of host capacity**" for A1 is common in busy regions — retry later, try
another availability domain, or use the AMD micro shape meanwhile; upgrading to Pay-As-You-Go keeps
Always Free resources free but needs a card (your decision). **Idle reclamation**: Oracle may reclaim
Always Free instances idle for 7 days (CPU p95 < 20 %, network < 20 %, memory < 20 % on A1) — a
classroom VM is idle most of the week, so keep the off-VM backups (§4.6) and these steps to recreate
it; check the instance the day before each lesson.

### 4.2 One-time provisioning (MANUAL — needs your Oracle account; not executed)

1. Oracle Cloud sign-up with home region Singapore. Create a VCN with internet connectivity (wizard).
2. Create instance: Canonical Ubuntu 24.04 (aarch64), `VM.Standard.A1.Flex` 1 OCPU / 6 GB, public
   IPv4, your SSH public key.
3. Security list (VCN) ingress: TCP 22 from **your IP only**, TCP 80 and TCP 443 from 0.0.0.0/0,
   optional UDP 443 (HTTP/3). **Never** open 3001.
4. OS firewall — Oracle's Ubuntu images reject everything except SSH in iptables (rules persisted by
   `netfilter-persistent`, preinstalled on those images). Idempotent (a rule is added only if missing):
   ```bash
   for rule in "-p tcp --dport 80" "-p tcp --dport 443" "-p udp --dport 443"; do   # udp 443 = optional HTTP/3
     sudo iptables -C INPUT -m state --state NEW $rule -j ACCEPT 2>/dev/null || sudo iptables -I INPUT 6 -m state --state NEW $rule -j ACCEPT
   done
   sudo netfilter-persistent save
   ```
5. DNS (your hostname, e.g. `quiz.<your-domain>`): an `A` record → the instance's public IP. Wait until
   `dig +short quiz.<your-domain>` returns it (Caddy needs this to obtain the certificate).

### 4.3 Install (on the VM)

Every command below is safe to re-run and works on arm64 (Ampere A1) and x86-64: NodeSource and the
Caddy repository publish arm64 packages; better-sqlite3 downloads a prebuilt linux-arm64 binary during
`npm ci` (the build tools are the fallback if none matches). No browser is needed on the VM.

```bash
sudo apt update && sudo apt -y upgrade
sudo apt -y install build-essential python3 rsync git sqlite3   # build tools only if a native module needs compiling
# Node.js 22 LTS (tested: the full unit suite, build, deploy smoke and restart E2E pass on Node 22.14)
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash - && sudo apt -y install nodejs
# Caddy (official apt repository)
sudo apt -y install debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt -y install caddy
# service user and directories: code read-only, data private
id -u hc >/dev/null 2>&1 || sudo useradd --system --home /opt/hidden-connection --shell /usr/sbin/nologin hc
sudo mkdir -p /opt/hidden-connection /var/lib/hidden-connection/backups
sudo chown -R hc:hc /var/lib/hidden-connection && sudo chmod 700 /var/lib/hidden-connection
```

### 4.4 Deploy the code (from the Mac, then on the VM)

```bash
# Mac — copy the working tree (no node_modules, local data, media sources, git history or legacy images)
rsync -az --delete --exclude node_modules --exclude dist --exclude data --exclude backups --exclude logs \
  --exclude .git --exclude media-src --exclude media-build --exclude media-tools \
  --exclude server/media/clues --exclude docs/clue-contact-sheet.jpg \
  ./ ubuntu@<vm-ip>:/tmp/hidden-connection/
# VM
sudo rsync -a --delete /tmp/hidden-connection/ /opt/hidden-connection/
cd /opt/hidden-connection && sudo npm ci && sudo npm test && sudo npm run build && sudo npm prune --omit=dev
sudo chown -R root:root /opt/hidden-connection          # the service user cannot modify the code
# environment (root:hc 0640) — created once; a re-run keeps the existing file and password.
# Secrets live only here on the VM, never in the repository (the template has an empty password).
[ -f /etc/hidden-connection.env ] || sudo install -m 0640 -o root -g hc deploy/hidden-connection.env.example /etc/hidden-connection.env
sudo grep -q '^ADMIN_PASSWORD=..' /etc/hidden-connection.env || sudo sed -i "s|^ADMIN_PASSWORD=.*|ADMIN_PASSWORD=$(openssl rand -base64 18 | tr -d '/+=')|" /etc/hidden-connection.env
sudo grep ADMIN_PASSWORD /etc/hidden-connection.env      # store it in your password manager
# service
sudo install -m 0644 deploy/hidden-connection.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now hidden-connection
systemctl status hidden-connection --no-pager && curl -s http://127.0.0.1:3001/api/health
# Caddy
sudo install -m 0644 deploy/Caddyfile /etc/caddy/Caddyfile
sudo mkdir -p /etc/systemd/system/caddy.service.d
printf '[Service]\nEnvironment=HC_SITE=quiz.<your-domain>\nEnvironment=ACME_EMAIL=<you@example.org>\n' | sudo tee /etc/systemd/system/caddy.service.d/hidden-connection.conf >/dev/null
sudo systemctl daemon-reload && sudo systemctl restart caddy && journalctl -u caddy -n 30 --no-pager
```

`npm test` on the VM is the arm64/Node 22 check of better-sqlite3 (`npm ci` fetches its prebuilt binary,
or compiles it with the build tools).

### 4.7 Process management and persistence (what was tested)

`e2e/deploy-smoke.mjs` reads `deploy/hidden-connection.service` and starts the server with its
`ExecStart` command and an `EnvironmentFile` built from `deploy/hidden-connection.env.example`, under a
supervisor with the unit's `Restart=on-failure` / `RestartSec=2` semantics, behind the real Caddy with
`deploy/Caddyfile`. SIGKILL in the middle of a 60 s production round → restart after 2 s → all 8 sockets
(admin, 5 teams, 2nd device, projector) reconnect through Caddy in 2.8–7.1 s; same round, original
deadline, the recorded submission is kept and a second one still refused; the round closes on time and
6/6 receive the results; SIGTERM → exit 0 in ≈ 1 s and **no** restart; the SQLite file afterwards holds
the room, the closed round with its original deadline and the submission. **systemd itself was not run**
(macOS); the unit is used on the VM as written (MANUAL check: `sudo systemctl kill -s SIGKILL
hidden-connection` during a test round, then `systemctl status` shows it restarted).

## 5. Caddy configuration

`deploy/Caddyfile` (validated with Caddy v2.11.7; used unchanged by the smoke test):

- one site `{$HC_SITE}`, automatic HTTPS (HTTP → HTTPS redirect, certificate renewal);
- `reverse_proxy 127.0.0.1:3001` — WebSocket upgrade handled automatically; `flush_interval -1` (no
  buffering of socket frames or media bytes); `stream_close_delay 2h` so a config reload never drops a
  running game; no stream timeout;
- Caddy sets `X-Forwarded-For` from the TCP peer and ignores client-sent values (no `trusted_proxies`)
  → origin `TRUST_PROXY=loopback`;
- headers: HSTS (1 year, no preload), CSP `default-src 'self'` (media from `blob:`, sockets `wss://`
  same host, `frame-ancestors 'none'`), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy:
  no-referrer`, no `Server` header; tested: a full round in Chrome over HTTPS/WSS with no CSP error;
- `encode zstd gzip` for text only (MP4 is never compressed — verified);
- `skip_install_trust` (never touches the OS trust store; only relevant to `tls internal` in tests).
