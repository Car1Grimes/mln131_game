## B. Audio phase state machine (projector, master ON)

| Phase | Audio |
|---|---|
| lobby | `lobby.mp3` loop; generic intro effect preloaded |
| intro | `intro.mp3` once, aligned, cut at the active start |
| active | `question.mp3` once, aligned to `startedAt`, stopped at the deadline; generic result effect **preloaded only** (after the first visual) |
| revealed | on a **live** `active → revealed` of that round: question source released, then `result.mp3` once (no loop), then silence; otherwise silence |
| ready | silence (intro preload allowed) |
| finished | `lobby.mp3` from 0, loop (stops a still-playing Q6 result) |

When music is OFF, nothing is fetched or played. Only one `<audio>` element exists, so two sources can never overlap.

## D. Preload and once-only logic

**Transition guard.** The controller remembers the last *live* view: connected, and a fresh view rather than the stale one kept across a disconnect.

- **When it plays.** A result is armed only when that previous live view was `active` for round *R* and the new one is `revealed` with `reveal.roundId === R`.
- **One attempt per round.** *R* is then consumed (`resultsSeen`), even when music is OFF. The result target exists only while `resultArmed === R`.
- **Leaving the effect ends it for good.** `resultArmed` is cleared on OFF, or when the track changes (ready, finished, the next round).
- **What can never trigger it:**
  - duplicate or unrelated revealed states (the target key `room:result:R` is stable);
  - OFF/ON;
  - mounting or refreshing on the revealed phase (no live history);
  - a disconnect (history is cleared, so a close missed offline never sounds late).
- **Failure statuses stick.** `ended`, `blocked` and `unavailable` are terminal for that target, so there is no retry storm.

**Preload.**

- **When.** While enabled, one fetch per active round, started after that round's first visual, so it never competes with the opening video or question audio. The blob is kept, and reused by later rounds until OFF or a decode error.
- **Abandoned preloads.** A preload still pending at the reveal is aborted, and playback fetches once on its own. A late response after the phase moved on is discarded by the generation guard; no Blob URL is created.
- **Cleanup.** The question Blob URL is revoked before the result's is created. All URLs are revoked on change, OFF and dispose.

## E. Server authorization

`GET /api/screen/rooms/:code/music/result`:

- **Session:** requires an unexpired, unrevoked `screen` bearer session bound to that room. Admin, team and other-room projector sessions get 403; no token gets 401.
- **Phase:** allowed only when the effective phase is `active` (preload) or `revealed` (playback). It returns 403 in lobby, intro, ready and finished.
- **Unchanged protections:** fixed allowlist, realpath containment, `audio/mpeg`, `private, no-store`, nosniff and same-origin. A missing file returns 404 only after authorization. No public static route exists, and video/scene media delivery is unchanged.

## G. Adding or replacing result.mp3

1. Place an authorized MP3 at exactly `server/media/music/result.mp3`, with a lowercase `.mp3` extension, readable by the server. No rebuild is needed.
2. Keep it short (a few seconds). It plays once from the start and is cut only when the operator advances. A long file therefore keeps sounding on the result screen until **Câu tiếp theo**.
3. When ready, commit it like the other supplied tracks; `.gitignore` already allows this exact path.
4. In rehearsal, with music ON, end a question and confirm the effect starts right as results appear. Also check its loudness against `question.mp3`, and that toggling OFF/ON or reloading `/screen` on the results does not replay it.
