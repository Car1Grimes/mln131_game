## 1. Harness

`e2e/bench.mjs` (Node clients with `socket.io-client`, plus one Chrome page): one room, 5 team clients
(+ one browser device of team 1), admin and a real 60 s round. Per metric: **min / median / p95 / max /
n**. It prints no token, PIN, password or answer (submissions use a dummy text).

| Metric | How |
|---|---|
| HTTP(S) connection | 30 fresh connections to `/api/health`: TCP connect, TLS ready, total |
| Socket.IO handshake | `connect()` → `connect` event (WebSocket upgrade + Socket.IO handshake + auth), 30 sockets |
| Socket.IO RTT | the app's `time:sync` event, 30 per team |
| Server event → client receipt | every `state` frame: local receipt time + clock offset − `serverNow` in the frame. The offset comes from the lowest-RTT `time:sync` sample; its uncertainty is ± half that RTT (0.1 ms locally, **≈ 66 ms on the simulated Wi-Fi**, where these values therefore mostly reflect the one-way delay) |
| Scene release → client receipt | receipt (server clock) − the scene's `releasedAt` |
| Scene release → visible | browser: `data-scene-id` change of the stage (the scene is shown only once its media is ready) − `releasedAt` |
| MP4 | each team downloads every released clip with its token, as the app does: TTFB, total, bytes, throughput; release → downloaded |
| Submission ACK | five simultaneous `team:submit` at 30 s (first), then idempotent retries of the same submission (same path, no insert) |
| Reconnect | transport dropped by the client (`engine.close()`), 3 × 5 teams: until `connect`, until the next `state`. Includes Socket.IO's default first-retry delay of 0.5–1.5 s, which the app uses |
| Results | deadline → `reveal` receipt |

Commands: `npm run bench` (local), `BENCH_PROFILE=wifi npm run bench`, `BENCH_QUESTION=3 …`,
`BENCH_TARGET=https://… BENCH_ADMIN_PASSWORD=… npm run bench`, `BENCH_MODE=fairness npm run bench`,
`node e2e/media-compare.mjs`. JSON with `OUT=<file>`.

Also measured in every run: the browser downloaded each released clip **exactly once** (4/4 and 6/6, 0
duplicates, nothing before release); every team downloaded 1 064 117 B (Q1) / 2 138 824 B (Q3) =
the released clips only; all sockets used the WebSocket transport (`wss` through Caddy); media responses
kept `Cache-Control: private, no-store, max-age=0`, no ETag, no `Content-Encoding`.

Reading:
- Gameplay events are fast everywhere: on the simulated weak link a state change reaches a phone in
  ≈ one one-way delay, a native (text/date/statistic) scene is visible ≈ 120 ms after release, and a
  submission is acknowledged in ≈ one RTT (≈ 0.2–0.28 s).
- Caddy + TLS add ≈ 2 ms to connection setup and ≈ 10 ms to MP4 TTFB on loopback: negligible.
- Video scenes are the only slow item: on the simulated 2.5 Mbit/s link a clip becomes visible
  **≈ 1.0–1.3 s (median) and up to 2.3 s** after its release, because the whole file is downloaded first.
- Reconnect ≈ 1–2 s, dominated by the client's retry delay (0.5–1.5 s by design), not by the server.
- One observation: five simultaneous first submissions are processed one after another (each ≈ 2–3 ms
  locally: insert + broadcast to all roles), so on a single machine their `receivedAt` values spread by
  ≈ 10 ms in arrival order. Order is preserved (FIFO); see §4.

## 3. Video delivery: fetch → Blob vs progressive playback (LOCAL / SIMULATED NETWORK)

The app downloads each released clip completely (authenticated `fetch`), then plays it from a Blob URL.
This keeps the token out of URLs and gives exactly one download per clip. `e2e/media-compare.mjs`
measures, on the same clips and with the same response headers, the time from "start loading" to the
first frame playing for (a) the app's Blob method and (b) `<video src=URL>` (the browser streams with
Range requests). Fresh connection and browser context per measurement, 5 trials each, alternating order.

| Clip (production) | **LOCAL**: Blob / progressive (median ms) | **SIMULATED NETWORK** weak Wi-Fi: Blob / progressive (median ms) | Saved on the simulated link |
|---|---|---|---|
| c17 — 78 KB | 31 / 35 | 509 / 418 | 0.09 s |
| c26 — 169 KB | 29 / 26 | 814 / 446 | 0.37 s |
| c19 — 302 KB | 43 / 51 | 1 210 / 456 | 0.75 s |
| c02 — 594 KB | 40 / 46 | 2 236 / 652 | 1.58 s |
| c04 — 816 KB (largest) | 36 / 40 | 2 898 / 693 | **2.21 s** |

Locally there is no difference. On a 2.5 Mbit/s link, progressive playback starts the large clips
1.6–2.2 s sooner (the in-app benchmark agrees: video visible at 1.0–1.3 s median, 2.3 s max). That is
meaningful in a 60 s round with a decisive clue at 45 s, so a change is **proposed, not implemented**:

- **Proposal (M4.2 candidate):** keep the endpoint and its rules, add a short-lived, single-asset media
  ticket (issued by the server only for a released scene, bound to the session, round and asset,
  expiring after e.g. 30 s, `Referrer-Policy: no-referrer`) so `<video src>` can stream with Range
  requests; time gating, "no future media", per-room checks and `no-store` stay as they are.
- **Costs/risks to evaluate first:** a URL token can appear in proxy or CDN logs (short expiry
  limits it); Range requests are several requests per clip (not "one download"); if a link is slower
  than a clip's bitrate (≈ 0.13–1.1 Mbit/s for these clips) streaming can stall where the Blob method would only
  start later; reconnect/seek behaviour must be re-tested. Stalls were **not** measured.
- **Without code changes:** the Blob pipeline is adequate on any link ≥ 10 Mbit/s (expected ≤ 0.7 s
  for the largest clip). Decide after real 4G/5G measurements (§6); if phones are on a good classroom
  Wi-Fi or 4G, the gain shrinks to the local numbers.

## 4. Latency and fairness (SIMULATED NETWORK)

Rules unchanged: the server receipt timestamp decides the order; client clocks are never trusted.
`BENCH_MODE=fairness`: five teams on links with fixed one-way delays 0 / 25 / 50 / 100 / 200 ms, all
sending at the same instant, 6 trials per scenario (two rooms × questions).

| Scenario | Answer order (server) | Send → receipt per team, median (ms) | ACK RTT per team, median (ms) |
|---|---|---|---|
| All send at the same instant | 1-2-3-4-5 in 6/6 trials | 2.2 / 27.6 / 53.7 / 102.5 / 203.1 | 6.7 / 56.3 / 107.6 / 207.4 / 408.3 |
| Team 5 (200 ms) sends 150 ms earlier | 1-2-5-3-4 in 6/6 | 2.2 / 27.1 / 55.3 / 101.2 / 203.2 | 5.1 / 56.2 / 108.6 / 206.7 / 406.7 |
| Team 5 (200 ms) sends 250 ms earlier | 5-1-2-3-4 in 6/6 | 1.2 / 27.1 / 51.3 / 101.3 / 203.8 | 5.2 / 55.0 / 105.4 / 205.8 / 407.2 |

Observed: the order is exactly "send time + uplink delay", deterministic and FIFO; a team's handicap
equals its one-way delay (here up to 0.2 s). On the simulated Wi-Fi with jitter (§2), the ACK RTTs of
five simultaneous submissions spread over 178–282 ms, i.e. receipt differences of up to ≈ 50 ms caused
by the network alone.

Assessment and mitigations (recommendations only — **nothing implemented**, no ping compensation, no
new scoring rule): differences of 0.05–0.2 s matter only when two teams answer within that window. If
real-device measurements show large disparities: (1) put all phones on the same classroom network
(the biggest lever; equalises the delays); (2) show the admin each team's connection RTT so a team on a
bad link can switch network before the round; (3) as a separately decided rule change, treat receipts
within a small window as a tie. Ping compensation is not recommended: it would trust client-reported
timing.

## 6. NOT MEASURED (expectations only)

- **External RTT** (Vietnam ↔ Oracle Singapore, or ↔ the nearest Cloudflare edge for Mode A): not
  measured. Every gameplay metric above grows by about one RTT (state, ACK) or one one-way delay
  (scene receipt); the TLS + WebSocket setup adds ≈ 2–3 RTT once per connection.
- **Real 4G/5G**: bandwidth, jitter and radio wake-up delays are unknown. With the Blob pipeline the
  video delay is ≈ TTFB + clip size ÷ effective bandwidth (arithmetic: the largest clip, 816 KB, takes
  ≈ 3.3 s at 2 Mbit/s and ≈ 0.7 s at 10 Mbit/s); not measured on phones.
- **Server load on the VM**: 7 devices are far below any limit (local run: ≈ 76 MB of media per full
  game; 7 clips released at once on the 50 Mbps AMD micro shape ≈ 1 s — arithmetic, not measured).
- **Cloudflare Quick Tunnel**: extra hop through the nearest edge; behaviour of `X-Forwarded-For`,
  caching (`cf-cache-status`) and WebSockets to be confirmed with `npm run bench` against the tunnel URL.

## 8. Recommendation

1. **Classroom: Mode B** — one Oracle Always Free **Ampere A1** VM in **Singapore**, Caddy in front,
   systemd. Measured overhead of the proxy/TLS is negligible; persistence, restart and reconnection
   behaviour are tested with the shipped Caddyfile and unit semantics. Use the AMD micro shape only if
   A1 capacity is unavailable.
2. **Mode A only for synthetic trials** from real phones (it measures the external path for free), not
   for lessons: no uptime guarantee, random URL, Cloudflare's video terms.
3. **Keep the Blob media pipeline for M4.1.** Measure on real phones first (`npm run bench` against the
   VM). If video scenes appear more than ≈ 1 s after release on the classroom network, implement the
   media-ticket streaming of §3 in M4.2 (expected gain up to ≈ 2 s on the largest clips at 2.5 Mbit/s).
4. Fairness: no rule change; prefer one shared classroom network. Revisit only with real-device data.
