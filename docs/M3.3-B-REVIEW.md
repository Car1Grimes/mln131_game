and (b) the server's receipt order read from the database — never with `shared/scoring.ts` or the
engine. Ranks: own competition ranking (1, 1, 3), ties in slot order. Points 50/40/30/20/10 by order of
correct answers. Checked per round: one recorded answer per submitting team, recorded text = confirmed

renders settles on the independent totals; each team's result card; projector reveals the right answer.

## 12. Investigation of the intermittent `resilience` Q4 failure (final gate)

**Symptom.** Once, in the long regression sequence: Run B, team 2's network frozen by the proxy, answer
confirmed, `getByTestId('delivery-uncertain').waitFor({ timeout: 10_000 })` timed out. Re-runs passed.

**Instrumentation (test-only, `e2e/resilience.mjs`).** For the Run B incident: test-process timestamps
(wall clock + monotonic `process.hrtime`) for proxy freeze, confirm click, waitFor result, reload, proxy
unfreeze, "recorded" visible; every `team:submit` frame sent by the browser and every acknowledgement
received (event name, ack id and the ack's `ok/error/duplicate` flags only — no payload, no token, no
PIN, no answer text); an in-page MutationObserver log of which delivery indicator is on screen
(`Date.now` + `performance.now`); the server's submission rows for team 2. Printed as a `DIAG` line,
and dumped if the wait fails.

**Event sequence measured (identical in all 10 runs before the fix; times after the confirm click):**

| t | Event |
|---|---|
| 0.00 s | proxy frozen, confirm clicked, `team:submit` emitted (ack #6), state `sending` → "Đang gửi …" |
| 5.00 s | Socket.IO acknowledgement timeout (5 s) → `offline` → state `uncertain` → "Chưa xác nhận được … Đang gửi lại…" |
| 5.30–5.40 s | Playwright's `waitFor` sees it |
| **6.00 s** | automatic retry after 1 s backoff (same submission, ack #7) → state `sending` → **back to "Đang gửi …"** |
| 11.00 s | next `uncertain` window (would last 2 s, then 4 s, 8 s …) — **after the test's 10 s budget** |
| ≈ 6.7 s | page reload (while frozen) — the pending answer is restored as `uncertain` |
| ≈ 9.7 s | proxy unfrozen → held frames delivered: server records the answer once (receipt 9.70–9.84 s); acks #6 `new`, #7 `duplicate` (same submission id) |
| +1.11–1.30 s after unfreeze | "Đã ghi nhận" visible; server rows for team 2 = **1** |

**Classification.**

| Hypothesis | Verdict | Evidence |
|---|---|---|
| E. Proxy inconsistent with the scenario | ruled out | server received nothing until the unfreeze in every run; held frames delivered in order; exactly one recorded row |
| C. React state race | ruled out | state transitions at exactly 5.00 s and 6.00 s in all runs (deterministic timers) |
| **D. Delivery-state bug** | **confirmed (presentation)** | after an unacknowledged attempt, each automatic retry switched the screen back to the neutral "Đang gửi …"; the "Chưa xác nhận" warning — required by `delivery.ts` ("reported as *unconfirmed*") and by CLASSROOM_DRY_RUN step 5 — was visible only 1 s, 2 s, 4 s … between retries on a stalled-but-connected link (typical weak classroom Wi-Fi) |
| A/B. Load or event-loop delay | likely trigger of the single miss, not proven | the assertion could only pass inside a fixed 1.00 s window (5–6 s); any delay > ≈ 1 s in Playwright's polling or the page would miss it. Not reproduced: 5 isolated + 5 runs under 16 CPU busy-loops on 8 cores all passed with the identical 1.00 s window |

**Fix (product, `src/player/delivery.ts` + `PlayerApp.tsx`).** New pure `deliveryView(state)`: the first
attempt shows "sending"; once an attempt went unacknowledged, retries in flight are shown as
"uncertain" ("Chưa xác nhận được … Đang gửi lại…"). The state machine, retry timing (1/2/4/8 s backoff),
submission id, locking and server behaviour are unchanged; the 10 s test timeout is unchanged (not
raised).

**Regression tests.** Unit (`src/player/delivery.test.ts`, +4): retries stay "uncertain" through 6
timeout/retry cycles with the original submission id; restored pending answers are "uncertain";
accepted/rejected unchanged; the view never unlocks editing. E2E (`e2e/resilience.mjs`): once "Chưa xác
nhận" appears it must stay on screen until the reload — **fails on the old build** (`delivery-sending`
relapse, 28/29) and passes on the fixed build (29/29 × 3, "uncertain from +5000 ms" continuously).

**Preserved and observed in every run:** never "recorded" without the server's view; answer locked while
pending; retry carries the original submission id (ack `duplicate`); one accepted submission; no
cross-round submission (unit + fullgame probes); deadline server-authoritative.
