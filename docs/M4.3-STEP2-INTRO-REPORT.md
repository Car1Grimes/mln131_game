## B. State machine and persistence

```
lobby/ready ──admin:start──▶ intro (5 s) ──server time──▶ active (40 s) ──deadline──▶ revealed ──advance──▶ ready | finished
```

**No schema migration.** At the accepted start command the server inserts the round row immediately, in the same transaction as before, with:

- `started_at = command + 5000`, which is the active start;
- `deadline_at = started_at + 40000`.

The room row is stored as `active`. `GameEngine.room()` derives the effective phase: `intro` while a stored-`active` room's open round has `now < started_at`. `intro` is never written; the `StoredPhase` type enforces this. This persists everything needed for the intro:

- **No duplicate rounds.** The round exists from the command, and `UNIQUE(room, question, kind)` holds.
- **Repeated starts are refused.** `admin:start` during the intro is refused with `wrong_phase` (`cannot start from intro`).
- **The boundary needs no write.** Intro → active is a function of the server clock, so a late timer cannot delay it.
- **Restart is exact.** `recover()` re-arms a broadcast timer at the original `started_at`. A restart during the intro resumes the remaining time and activates at the original moment. A restart after the boundary comes back active at the correct scene offset. A restart past the deadline closes the round once.
- **Rejected alternative.** An explicit stored `intro` phase would have needed rebuilding the `rooms` table (SQLite CHECK constraint) on the real classroom database, plus a timed write at the boundary. Both are avoidable risks.

**Everything keys off `started_at`, so nothing of the round exists before it:**

- **Views:** `round` is `null` during the intro. The new `intro` field carries only `{questionNumber, totalQuestions, prompt, introStartedAt, startsAt}`. There is no round id, scene, answer shape or media id.
- **Media:** `authorizeMedia` refuses every asset before `started_at` (an explicit check, plus the original release-time check).
- **Submissions:** an answer for the pending round, with or without `roundId`, gets `wrong_phase`. A lost-ack retry of the previous question still reconciles to its original receipt, and nothing is recorded in the new round. A defence-in-depth check also rejects `receivedAt < started_at`.
- **Other paths:** rename is refused during the intro. `/api/admin/rooms` reports the effective phase.

## C. Timing contract

| Quantity | Value | Source |
|---|---|---|
| Intro | `INTRO_DURATION_MS = 5000` (shared/protocol.ts); fixed in production (tests may shorten it, never lengthen it) | server clock at command acceptance |
| Active start | `startedAt = command + 5000` | persisted |
| Deadline | `deadlineAt = startedAt + 40000` | persisted, unchanged rule |
| Command → deadline | 45 000 ms | |
| Scene releases | `startedAt + scene.at` (0–40 000 ms, unchanged) | |
| Response time / scoring | `received_at − startedAt` (intro excluded) | unchanged formula |

- **Who decides the switch.** The server pushes the active view at `startedAt`. Clients render the countdown from `startsAt − (Date.now() + measured offset)`, ticking at 100 ms during the intro. They never switch phase on their own timer; at 0 they hold "1"/"Bắt đầu!" until the server's view arrives.
- **Late joiners and refreshes** compute the remaining time and never restart from 5.

## E. Audio

The new optional file is `server/media/music/intro.mp3`. It is already covered by the existing `.gitignore` rule `server/media/music/*.mp3`, and has the same containment, projector-only bearer session and `private, no-store` headers as the other tracks.

| Phase | Behavior when music is ON |
|---|---|
| lobby | lobby.mp3 loops; generic intro effect preloaded once |
| intro | lobby stopped; intro effect plays once, aligned to `introStartedAt`; cut at `startsAt` by an independent timer (even without a new view) |
| active | existing question behavior (waits for first visual, aligned to `startedAt`) |
| revealed / ready | silence (ready may preload the generic effect, no playback) |
| finished | lobby.mp3 from 0, loops |

**Where the intro track is served.** The `intro` track endpoint answers only in lobby, ready and intro, so a generic, question-independent preload is possible. It refuses active, revealed and finished. The question track is still refused during the intro, and lobby and question audio are never prefetched.

**Preload rules:**

- At most one attempt per lobby/ready phase.
- A pending preload is aborted when its waiting phase ends.
- OFF drops the cache, so ON re-reads the server file.
- A decode error drops the cache, so a replaced file is fetched next time.

**Failure handling.** A missing, corrupt, delayed or autoplay-blocked effect is reported in the existing status line. None of these affects the visuals or timing; the intro never waits for audio. A view update never restarts the effect (its identity is `room:intro:startsAt`). One `<audio>` element is used throughout, so lobby, intro and question audio cannot overlap.

## H. Regressions and open issues

- **Smaller projector video.** The projector video frame is about 7.6% smaller (1440 → 1330 px wide at 1920×1080) to make room for the prompt above it. The player and admin layouts are unchanged because the prompt sits in the existing header row. If the projector frame must keep its full size, the alternative is a one-line prompt inside the side column. That would not satisfy "above SceneStage".
- **Intended behavior changes:**
  - In ready (and lobby), Music ON now fetches the generic intro effect.
  - Every start takes 45 s to the deadline instead of 40 s.
- **Not exercised:**
  - Real audio files: only generated fixture tones were used.
  - Safari/iOS autoplay.
  - Physical speaker and projector output.
- **Known limit:** the intro countdown display depends on the measured clock offset, like the existing round timer. The phase switch itself does not.
